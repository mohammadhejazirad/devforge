# AGENTS.fa.md — پروژه DevForge (نام موقت)

راهنما برای ایجنت‌های هوش مصنوعی که روی این مخزن کد می‌نویسند. قبل از نوشتن کد، همه‌ی این فایل را بخوانید. نسخه‌ی انگلیسی در `AGENTS.md` است و هر دو فایل باید همگام بمانند. اگر تفاوتی بود، نسخه‌ی انگلیسی مرجع است.

---

## ۱. چشم‌انداز پروژه

DevForge یک ابزار هوشمند ترمینالی برای آماده‌سازی محیط توسعه و مدیریت نسخه‌ها روی لینوکس (دسکتاپ و سرور) است. بعد از نصب تازه‌ی سیستم‌عامل، برنامه‌نویس باید در چند دقیقه آماده‌ی کار شود، نه چند ساعت.

این ابزار موارد زیر را نصب، بروزرسانی، جابه‌جا، پین و حذف می‌کند:

- زبان‌ها و runtime ها: PHP، Node.js، Go، Python، Rust، Java، Ruby، .NET، Bun، Deno
- مدیر نسخه و ابزار پکیج: NVM، NPM، pnpm، Yarn، Composer، pipx، uv، pyenv
- زیرساخت: Docker (و Compose)، Git، kubectl، Helm، Terraform
- دیتابیس و سرویس‌ها: MySQL/MariaDB، PostgreSQL، Redis، Nginx، Caddy
- ابزارهای کمکی: build-essential و معادل‌ها، curl، jq، tmux، ripgrep، کلید SSH، تنظیم shell و غیره

نگاه شما باید ترکیب یک **مهندس ارشد DevOps، ادمین ارشد لینوکس و مهندس ارشد نرم‌افزار** باشد. ابزار باید به‌طور پیش‌فرض امن و idempotent باشد، قبل از هر کار بگوید چه می‌کند و روی شبکه‌ی ضعیف هم کار کند.

نحوه‌ی توزیع عمومی: کاربر با کپی کردن یک دستور از گیتهاب نصب می‌کند، مثلاً:

```bash
curl -fsSL https://raw.githubusercontent.com/<owner>/<repo>/main/install.sh | bash
```

## ۲. الزامات غیرقابل مذاکره

1. **همه‌ی متن‌های برنامه فقط انگلیسی باشند** (منو، پرسش‌ها، لاگ، خطا، `--help`)، چون فارسی در ترمینال خوب پشتیبانی نمی‌شود. هیچ متن راست‌به‌چپی در خروجی برنامه نباشد. مستندات می‌توانند دو‌زبانه باشند، خود برنامه نه.
2. **فقط ترمینال** (CLI و منو/پرسش تعاملی). وابستگی به GUI نباشد، چه روی دسکتاپ و چه روی سرور.
3. **مستقل از توزیع.** هرگز «Ubuntu» را هاردکد نکنید. توزیع را از `/etc/os-release` (فیلدهای `ID`، `ID_LIKE`، `VERSION_ID`) و معماری را از `uname -m` تشخیص دهید. حداقل روی Debian/Ubuntu، خانواده‌ی Fedora/RHEL (Rocky، Alma، CentOS Stream)، Arch/Manjaro، openSUSE و Alpine (تلاش حداکثری) کار کند. اهداف مرجع: Ubuntu Desktop 26.04 و Ubuntu Server 24.04.5.
4. **دسکتاپ یا سرور نباید رفتار اصلی را تغییر دهد.** تشخیص آن (بخش ۶) فقط برای پنهان کردن گزینه‌های مخصوص GUI و تنظیم پیش‌فرض‌هاست.
5. **پشتیبانی از Mirror های ایرانی و تغییر DNS جزو قابلیت‌های اصلی است**، اختیاری و در کنترل کاربر (بخش ۷).
6. **چرخه‌ی کامل نسخه برای هر ابزار:** نصب، لیست نصب‌شده‌ها، لیست نسخه‌های موجود، بروزرسانی، تغییر نسخه‌ی پیش‌فرض، پین کردن برای هر پروژه، حذف، و doctor/verify.
7. **کیفیت مناسب مخزن عمومی:** امن برای pipe به bash، بدون secret، بدون telemetry به‌صورت پیش‌فرض، لایسنس MIT یا Apache-2.0، و راهنمای مشارکت روشن.

## ۳. انتخاب زبان و فناوری

- **نصب‌کننده‌ی اولیه: POSIX `sh` یا Bash** (`install.sh`). فقط این وظایف را دارد: تشخیص سیستم‌عامل، اطمینان از وجود `python3` (نسخه‌ی ۳.۹ به بالا؛ اگر نبود با پکیج‌منیجر سیستم و با اجازه‌ی کاربر نصب شود)، دانلود نسخه‌ی release پین‌شده، بررسی checksum، نصب در `~/.local/share/devforge`، ساخت symlink در `~/.local/bin/devforge` (یا `/usr/local/bin` برای root) و نمایش مراحل بعدی.
- **هسته: Python 3.9+ فقط با کتابخانه‌ی استاندارد** در مسیر اجرا (بدون وابستگی pip هنگام نصب). این کار در شبکه‌های تحریم‌شده یا آفلاین از شکست bootstrap جلوگیری می‌کند. امکانات اختیاری (مثل `rich`) اگر نبودند باید بدون مشکل کنار گذاشته شوند.
- از `subprocess` با لیست آرگومان استفاده کنید، هرگز `shell=True` با ورودی ترکیب‌شده.
- type hint همه‌جا؛ در CI از `ruff` و `mypy` و `pytest`، و برای shell از `shellcheck` و `shfmt` استفاده شود.

## ۴. ساختار پیشنهادی

```
install.sh                  # نصب‌کننده‌ی curl|bash
devforge/
  __main__.py               # نقطه‌ی ورود
  cli.py                    # argparse و زیردستورها
  tui.py                    # منوی تعاملی (با fallback استاندارد)
  core/
    system.py               # توزیع، معماری، init، دسکتاپ/سرور، root/sudo
    pkgmgr.py               # انتزاع apt/dnf/yum/pacman/zypper/apk
    net.py                  # دانلود، retry، resume، checksum، proxy
    mirrors.py              # پروفایل و اعمال mirror
    dns.py                  # نمایش/تنظیم/بازگردانی DNS
    state.py                # پایگاه وضعیت نصب (JSON) و بکاپ
    logging.py              # لاگ فایل و کنسول، حذف secret
    plan.py                 # موتور plan/apply و dry-run
  tools/
    base.py                 # اینترفیس Tool (پایین)
    node.py php.py go.py python.py docker.py ...
  data/
    mirrors/*.toml|json     # تعریف mirror ها (قابل ویرایش توسط جامعه)
    versions/*.json         # کش فهرست نسخه‌های upstream
tests/
docs/
AGENTS.md  AGENTS.fa.md  README.md  CONTRIBUTING.md  LICENSE
```

هر ابزار یک اینترفیس را پیاده می‌کند تا افزودن ابزار جدید فقط یک فایل باشد:

```python
class Tool(Protocol):
    name: str
    def detect(self) -> InstalledInfo: ...
    def available_versions(self) -> list[Version]: ...
    def install(self, version: str, *, make_default: bool) -> Plan: ...
    def update(self, version: str | None) -> Plan: ...
    def use(self, version: str, *, scope: Scope) -> Plan: ...   # global | project | shell
    def uninstall(self, version: str, *, purge: bool) -> Plan: ...
    def doctor(self) -> list[Check]: ...
```

## ۵. اصول رفتاری

- **اول plan، بعد apply.** هر دستور تغییردهنده یک plan می‌سازد، نشان می‌دهد، تأیید می‌گیرد (`-y/--yes` برای رد کردن تأیید) و از `--dry-run` پشتیبانی می‌کند.
- **Idempotent.** اجرای دوباره باید امن و سریع باشد.
- **حداقل دسترسی.** نصب در فضای کاربر (`~/.local` و پوشه‌ی نسخه‌ها برای هر کاربر) به نصب سراسری سیستم ترجیح دارد. `sudo` فقط در صورت نیاز، و قبل از درخواست دلیلش گفته شود.
- **هرگز بی‌صدا چیزی را خراب نکنید.** قبل از ویرایش فایل‌های پیکربندی بکاپ بگیرید (`*.devforge.bak`)، در حذف درباره‌ی پاک کردن داده‌ها بپرسید، و `rm -rf` روی مسیر محاسبه‌شده بدون اطمینان از اینکه داخل پوشه‌ی متعلق به DevForge است ممنوع است.
- **منابع رسمی و تأییدشده.** tarball و repo رسمی، کلید GPG و checksum SHA256. اسکریپت راه دور تأییدنشده را اجرا نکنید.
- **معنای تغییر نسخه** (مثال Node.js از ۲۴ به ۲۶): نسخه‌ی ۲۶ کنار ۲۴ نصب شود، ۲۴ بماند، پیش‌فرض به ۲۶ تغییر کند، پین برای هر پروژه با `.nvmrc` یا `.node-version` یا `.tool-versions` انجام شود، shim یا مدیریت PATH در bash/zsh/fish کار کند، و حذف تمیز ۲۴ در صورت درخواست ممکن باشد. همین الگو برای PHP (شامل CLI و FPM و `update-alternatives` در جای مناسب)، Go و Python.
- **به تنظیمات موجود احترام بگذارید.** nvm/pyenv/asdf/mise و پکیج‌های توزیع که از قبل هستند را تشخیص دهید و به‌جای بازنویسی، همزیستی یا adopt کنید.
- **ادغام با shell** صریح و برگشت‌پذیر باشد: بلوک مدیریت‌شده در فایل‌های rc با نشانگر شروع و پایان.
- **حالت غیرتعاملی** برای CI و سرور: برای هر پرسش یک flag باشد، exit code معنادار باشد و خروجی `--json` برای اسکریپت‌نویسی وجود داشته باشد.
- **پروفایل‌ها (preset)** مثل `web-php`، `node-fullstack`، `go-backend`، `devops` و فایل پیکربندی قابل export/import تا کاربر کل ماشین را با یک دستور بسازد: `devforge apply devforge.toml`.

## ۶. تشخیص محیط («هوشمند»)

این موارد از طریق `devforge doctor` و `devforge info` تشخیص و نمایش داده شوند:

- خانواده و نسخه و codename توزیع، معماری (amd64/arm64)، libc (glibc/musl)
- پکیج‌منیجر و init system (systemd/OpenRC/دیگر)، تشخیص container/WSL/VM
- دسکتاپ یا سرور: نبودن `DISPLAY` و `WAYLAND_DISPLAY`، خروجی `systemctl get-default`، `XDG_CURRENT_DESKTOP`، پکیج‌های محیط دسکتاپ. این فقط یک راهنماست، نه شرط سخت.
- وجود root/sudo، فضای دیسک، RAM، proxy موجود، و دسترسی به upstream های مهم (همراه با زمان پاسخ)
- توزیع یا نسخه‌ی پشتیبانی‌نشده یا خیلی جدید: با پیام روشن و fallback کار کند (مثلاً tarball رسمی به‌جای repo شخص ثالثِ هنوز ناموجود برای نسخه‌های تازه مثل Ubuntu 26.04). هرگز با stack trace شکست نخورد.

## ۷. تاب‌آوری شبکه: Mirror و DNS

هدف: در زمان تحریم، فیلترینگ و ناپایداری اینترنت بین‌الملل هم ابزار قابل استفاده بماند.

- **پروفایل mirror** در `data/mirrors/` و قابل انتخاب: `devforge mirror list|set|test|reset`. شامل مخازن پکیج سیستم‌عامل (apt/dnf/pacman و غیره)، رجیستری npm، PyPI، Composer/Packagist، پراکسی Go (`GOPROXY`)، mirror های رجیستری Docker، پراکسی دانلود GitHub، Maven، RubyGems و crates.
- فهرست mirror ها **داده‌ی نگهداری‌شده توسط جامعه** هستند، نه کد. آدرس فروشنده‌ها را در منطق برنامه هاردکد نکنید. دستور `mirror test` تأخیر و سرعت را بسنجد و بتواند بهترین را خودکار انتخاب کند، با امکان override کاربر. استفاده از mirror **اختیاری** است و پیش‌فرض همان upstream است.
- حتی با mirror، بررسی checksum و GPG روشن بماند تا محتوای درست تضمین شود.
- **کمک‌کننده‌ی DNS:** `devforge dns show|set|test|restore`. presetها را کاربر انتخاب می‌کند و هرگز بی‌صدا تغییر نمی‌کنند. resolver در حال استفاده (systemd-resolved، NetworkManager، resolvconf، یا `/etc/resolv.conf` ایستا) تشخیص داده شود و تغییر از مسیر درست انجام شود. همیشه بکاپ بگیرید و بازگردانی با یک دستور ممکن باشد.
- دانلودها: retry با backoff، resume، fallback چندمنبعی، رعایت `HTTP(S)_PROXY` و `NO_PROXY`، و پوشه‌ی کش آفلاین.
- هیچ بخشی نباید به آنلاین ماندن یک اپراتور mirror وابسته باشد.

## ۸. مستندات، تجربه‌ی کاربری و خروجی

- رشته‌های انگلیسی در یک مکان متمرکز تا یکدست بمانند. از نشانگرهای ASCII ساده (`[ok]`، `[warn]`، `[err]`) با رنگ اختیاری استفاده شود و `NO_COLOR` و خروجی غیر TTY رعایت شود.
- خطاها کوتاه و کاربردی: چه چیزی شکست خورد، چرا، و چه کاری بعدش انجام شود.
- `devforge --help` و راهنمای هر زیردستور کامل و همراه با مثال باشد.
- فایل لاگ در `~/.local/state/devforge/logs/` و با حذف secret ها.

## ۹. تست

- تست واحد برای منطق تشخیص با فایل‌های `os-release` نمونه از توزیع‌های مختلف.
- تست یکپارچه در container با ماتریس توزیع‌ها (Debian 12/13، Ubuntu 22.04/24.04/26.04، Fedora، Rocky/Alma، Arch، openSUSE، Alpine) با GitHub Actions.
- تست `install.sh` با `shellcheck` و در container تمیز، هم با `python3` و هم بدون آن.
- همه‌ی منطق تغییردهنده باید بدون root با `--dry-run` قابل تست باشد.
- هرگز تست مخرب را روی میزبان اجرا نکنید؛ از container یا VM استفاده کنید.

## ۱۰. امنیت

- نصب‌کننده از طریق HTTPS، پین‌شده به tag های release، با SHA256 منتشرشده (و در حالت ایده‌آل امضا).
- بدون `eval` روی محتوای راه دور؛ بدون متغیر quote‌نشده در shell؛ اعتبارسنجی همه‌ی رشته‌های نسخه با regex سخت‌گیرانه.
- هیچ اعتبارنامه‌ای ذخیره نشود. تا زمانی که کاربر صریحاً opt-in نکرده و مستند نشده، telemetry نباشد.

## ۱۱. قوانین کار برای ایجنت‌ها

1. قبل از هر تغییر وضعیت مخزن را بررسی کنید و کار موجود را بازنویسی نکنید.
2. به‌ترتیب جلو بروید: `core/system.py` (تشخیص) ← `pkgmgr` ← `state` و `plan` ← `net` و `mirrors` و `dns` ← اولین ابزارها (Node، Python، Go، Docker، PHP) ← TUI ← presetها ← بسته‌بندی.
3. هر تغییر همراه با تست و مستندات بروز بیاید. هر دو فایل `AGENTS` همگام بمانند.
4. از سبک موجود پیروی کنید؛ توابع کوچک و typed باشند؛ بدون بحث، وابستگی runtime جدید اضافه نشود.
5. هنگام توسعه، دستورهای تغییردهنده‌ی سیستم (نصب پکیج، تغییر DNS) را روی ماشین توسعه‌دهنده اجرا نکنید؛ از dry-run، fixture یا container استفاده کنید.
6. اگر نیازمندی مبهم بود، فرض خود را در توضیح commit یا PR بنویسید و بی‌صدا حدس نزنید.
7. سؤال‌های باز برای تأیید با نگهدارنده: نام نهایی پروژه، لایسنس، حداقل نسخه‌ی Python، و اینکه نسخه‌ها با shim اختصاصی مدیریت شوند یا با `mise`/`asdf` ادغام شوند.
